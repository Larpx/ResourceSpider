# 概述

ResourceSpider 是一个轻量、灵活、高性能、跨平台的分布式网络爬虫框架，可以帮助 .NET 工程师快速的完成资源爬虫的开发。

---

# 一、技术栈与架构要求

## 1.1 核心要求

1. 整个爬虫设计是纯异步的，利用消息队列进行各个组件的解耦。单机爬虫无需额外配置，默认使用内存型消息队列；分布式爬虫需引入外部消息队列。项目结果严格按照架构图实现，不能有任何偏差。

2. 爬虫系统整体分为 Agent 和服务端，Agent 负责下载数据，服务端负责协调和管理多个 Agent。当 Agent 没有连接到服务端的时候，则会默认读取本地的采集任务并将结果存放到本地中；若是连接到了服务端，则会将采集任务发送到服务端，服务端会根据任务的类型和优先级进行调度，并从服务端请求新的采集任务以更新自己的任务列表，如果完成采集任务，则进入等待状态。

3. 服务端负责任务的调度、分发、监控和管理。基于 ASP.NET Core 11.0 框架实现，提供 RESTful API 接口。服务端会监听指定的端口，接收来自 Agent 的请求，根据请求内容进行任务调度、分发、监控和管理。需要在服务端实现架构图中的 Interface 层、Service 层和存储层。

4. 整体项目可以参考 DotnetSpiderEx 目录下的代码去开发，根据需要修改和扩展，但不要直接引用该项目和该项目的 NuGet 包。

5. 数据访问：使用 SqlSugar.Core 库作为 ORM 框架，任务的存储建议可以缓存到 Redis 中，避免数据库压力过高，提高系统响应速度。

6. 数据库选择：采用 MySQL 作为数据库解决方案（考虑到与 .NET 生态的兼容性及部署便捷性）。

7. 部署方式：支持 Docker 容器化部署，需提供完整的 Dockerfile 及 docker-compose 配置文件。

8. 其他要求：要使用免费的Nuget包，不要使用收费的功能包。

9. 爬虫框架需要支持xpath、css选择器等解析器，用于从网页中提取数据，也需要可以自定义解析器。

## 1.2 系统架构设计

### 1.2.1 架构分层

系统整体采用分层架构设计，自上而下分为以下层次：

#### （1）Agent 层（数据采集层）
- **Agent 1/2/3**: 分布式数据采集节点，部署在不同机器上负责下载数据
- **Portal**: 管理门户，用于监控和管理整个爬虫系统

#### （2）Interface 层（接口层）
- **Portal 接口**: 提供统一的访问入口，通过 HTTP 协议与 Agent 和 Internet 通信

#### （3）Service 层（服务层）
- **Agent Register Service**: 下载代理器注册服务，接收 Agent 的注册和心跳
- **Statistics Service**: 统计服务，监控各个爬虫和下载代理器的运行状态
- **Spider Instance（爬虫实例核心）**:
  - **Concurrent Controller**: 并发控制器，控制请求的并发速度
  - **Request Supplier**: 请求供应接口，提供下载请求
  - **Request Configure**: 请求配置模块，统一处理请求配置（如签名等）
  - **DataFlow**: 数据流处理，包含解析器和存储器
  - **Scheduler**: 调度器，负责请求去重和采集顺序控制
  - **ProxyPool and detect**: 代理池和代理检测模块

#### （4）Storage 层（存储层）
支持多种存储方案，可根据实际需求选择：
- **MySql**: 关系型数据库存储
- **SqlServer**: SQL Server 数据库存储
- **Redis**: 缓存和任务队列存储
- **HBase**: 大数据存储
- **PostgreSql**: PostgreSQL 数据库存储

#### （5）Message Queue（消息队列）
- 位于 Service 层和 Storage 层之间，负责各个组件之间的异步通信和解耦
- 支持内存型消息队列（单机模式）和外部消息队列（分布式模式）

### 1.2.2 数据流向

1. Agent 通过 Internet 发送 HTTP 请求获取数据
2. 数据通过 Portal 接口进入 Service 层处理
3. Service 层通过消息队列进行组件间通信
4. 处理后的数据存储到 Storage 层

## 1.3 Agent 数据采集方法规范

### 1.3.1 采集方式分类

Agent 支持多种数据采集方式，根据目标网站特性选择合适的采集方案：

#### （1）HTTP 直连采集（推荐首选）
- **适用场景**: 静态网页、RESTful API、JSON 接口
- **实现方案**: 基于 `HttpClient` + `Refit` 库
- **优势**: 高性能、低资源消耗、支持高并发
- **配置项**:
  - `ConnectionTimeout`: 连接超时时间（默认 30 秒）
  - `RequestTimeout`: 请求超时时间（默认 60 秒）
  - `MaxConcurrentRequests`: 最大并发请求数
  - `RetryCount`: 失败重试次数

#### （2）无头浏览器采集
- **适用场景**: 动态渲染页面（SPA 应用）、需要 JavaScript 执行的页面、反爬机制严格的网站
- **实现方案**: 
  - **Playwright.NET**（推荐）: 支持 Chromium、Firefox、WebKit，提供完整的浏览器自动化 API
  - **PuppeteerSharp**: 基于 Chromium 的 Node.js Puppeteer 的 .NET 移植版本
- **技术选型建议**:
  - 优先使用 Playwright.NET，其 API 更现代化且支持多浏览器引擎
  - 需要截图或 PDF 导出时，使用无头浏览器的内置功能
- **配置项**:
  - `BrowserType`: 浏览器类型（Chromium/Firefox/WebKit）
  - `Headless`: 是否无头模式（默认 true）
  - `ViewportSize`: 视口大小配置
  - `Timeout`: 页面加载超时时间
  - `WaitUntil`: 页面加载完成条件（Load/DOMContentLoaded/NetworkIdle）

#### （3）自定义下载器
- **适用场景**: 特殊协议（FTP、WebSocket）、自定义加密传输
- **实现方式**: 实现 `IDownloader` 接口，自定义下载逻辑
- **注册方式**: 通过依赖注入注册自定义下载器

### 1.3.2 浏览器自动化最佳实践

#### 资源管理
- 使用对象池管理浏览器实例，避免频繁创建销毁
- 配置浏览器实例最大生命周期，定期重启防止内存泄漏
- 及时关闭未使用的标签页和上下文

#### 反爬策略应对
- 随机化 User-Agent 字符串
- 模拟人类行为：随机延迟、鼠标移动轨迹
- 使用代理 IP 池轮换
- 配置浏览器指纹随机化

#### 性能优化
- 禁用不必要的资源加载（图片、字体、CSS）
- 使用请求拦截跳过广告和追踪脚本
- 配置合理的页面加载超时策略
- 批量操作时复用浏览器上下文

## 1.5 Agent 运行模式规范

### 1.5.1 模式分类

Agent 支持两种运行模式，可通过配置文件进行切换：

#### （1）本地模式（Local Mode）

- **适用场景**: 
  - 离线环境下的数据采集
  - 简单采集任务（如单页面抓取、小规模数据采集）
  - 开发调试阶段
  - 网络不稳定的临时采集需求

- **工作特点**:
  - 独立运行，无需连接服务端
  - 从本地配置文件或本地文件读取采集任务
  - 采集结果存储到本地文件系统
  - 支持手动导入导出任务配置

- **配置项**:
  ```json
  {
    "Agent": {
      "Mode": "Local",
      "LocalConfig": {
        "TaskFilePath": "./tasks",
        "ResultOutputPath": "./results",
        "OutputFormat": "txt",
        "MaxConcurrentTasks": 5
      }
    }
  }
  ```

#### （2）在线模式（Online Mode）

- **适用场景**:
  - 分布式大规模数据采集
  - 需要统一管理和调度的采集任务
  - 实时性要求高的采集场景
  - 需要监控和统计的采集任务

- **工作特点**:
  - 连接服务端，接收服务端下发的采集任务
  - 实时上报任务执行状态和结果
  - 接受服务端的统一调度和管理
  - 支持动态配置更新

- **配置项**:
  ```json
  {
    "Agent": {
      "Mode": "Online",
      "ServerConfig": {
        "ServerUrl": "https://api.example.com",
        "AgentId": "agent-001",
        "AgentToken": "your-token",
        "HeartbeatInterval": 30
      }
    }
  }
  ```

### 1.5.2 本地模式数据存储格式

#### （1）TXT 格式

- **文件名规范**: `{AgentId}_{TaskId}_{Timestamp}.txt`
- **文件内容**:
  ```
  [Agent Info]
  AgentId: agent-local-001
  AgentName: Local Agent 01
  HostName: PC-Name
  Mode: Local
  CollectTime: 2024-01-01 12:00:00

  [Task Info]
  TaskId: task-001
  TaskName: 示例采集任务
  Url: https://example.com
  Status: Success

  [Data]
  字段1: 值1
  字段2: 值2
  ...
  ```

#### （2）CSV 格式

- **文件名规范**: `{AgentId}_{TaskId}_{Timestamp}.csv`
- **文件头**: 包含 Agent 信息字段和数据字段
- **格式示例**:
  ```csv
  AgentId,AgentName,HostName,CollectTime,TaskId,TaskName,Url,Status,字段1,字段2
  agent-local-001,Local Agent 01,PC-Name,2024-01-01 12:00:00,task-001,示例采集任务,https://example.com,Success,值1,值2
  ```

#### （3）JSON 格式（可选）

- **文件名规范**: `{AgentId}_{TaskId}_{Timestamp}.json`
- **结构**: 嵌套 JSON 对象，包含 Agent 信息、任务信息和采集数据

### 1.5.3 采集结果文件规范

#### 必填字段

所有采集结果文件必须包含以下 Agent 信息字段，确保数据来源可追溯：

| 字段名 | 说明 | 示例 |
|--------|------|------|
| AgentId | Agent 唯一标识 | agent-local-001 |
| AgentName | Agent 名称 | Local Agent 01 |
| HostName | 运行主机名 | PC-Name |
| Mode | 运行模式 | Local/Online |
| CollectTime | 采集时间 | 2024-01-01 12:00:00 |
| TaskId | 任务 ID | task-001 |
| TaskName | 任务名称 | 示例采集任务 |

#### 文件存储目录结构

```
results/
├── agent-local-001/
│   ├── 2024-01-01/
│   │   ├── agent-local-001_task-001_20240101120000.csv
│   │   └── agent-local-001_task-002_20240101130000.txt
│   └── 2024-01-02/
│       └── agent-local-001_task-003_20240102100000.csv
└── agent-local-002/
    └── ...
```

### 1.5.4 本地结果导入功能

#### 导入方式

Portal 后台管理需提供本地采集结果导入功能：

1. **文件上传导入**: 支持上传单个或批量上传采集结果文件
2. **目录扫描导入**: 指定本地目录，自动扫描并导入符合条件的结果文件
3. **拖拽导入**: 支持拖拽文件到上传区域

#### 导入流程

```
1. 选择导入方式（文件/目录）
   ↓
2. 选择采集结果文件
   ↓
3. 系统解析文件，提取 Agent 信息和采集数据
   ↓
4. 数据校验（格式、完整性、重复性）
   ↓
5. 预览导入数据
   ↓
6. 确认导入
   ↓
7. 数据存储到数据库
   ↓
8. 生成导入报告（成功/失败统计）
```

#### 数据校验规则

- **格式校验**: 验证文件格式是否正确（TXT/CSV/JSON）
- **完整性校验**: 检查必填字段是否完整
- **重复性校验**: 根据 TaskId + AgentId + 数据指纹判断是否重复
- **Agent 校验**: 验证 AgentId 是否在系统中注册（可选）

#### 导入报告

导入完成后生成导入报告，包含：

- 总文件数
- 成功导入文件数
- 失败文件数及失败原因
- 总数据条数
- 成功入库条数
- 跳过重复条数
- 导入时间

### 1.5.5 模式切换机制

#### 切换方式

- 通过修改配置文件中的 `Agent.Mode` 值切换模式
- 切换后需重启 Agent 服务生效

#### 切换注意事项

- **本地模式转在线模式**:
  - 需确保 Agent 已在服务端注册
  - 本地未完成的任务可选择上传到服务端或保留在本地
  
- **在线模式转本地模式**:
  - 服务端的任务会自动转为本地任务
  - 已分配的 Agent 任务会被释放

#### 混合模式支持（可选）

- 支持 Agent 同时配置多个任务，部分任务在本地执行，部分任务通过服务端执行
- 配置方式：在任务配置中指定 `ExecutionMode` 字段

# 二、核心模块设计

爬虫的基本流程是：下载数据（发送 HTTP 请求并获得返回的 response）-> 解析返回的文本（可以是 text、json、html）-> 存储解析到的数据，针对这三个主逻辑，我们可以再细下成以下模块。

- **Scheduler 调度器**: 用于对采集请求的去重、采集顺序控制，默认实现了广度优先和深度优先两种调度器。调度器可以采用不同的 Hash 去重器，通常使用默认的 HashSetDuplicateRemover 即可，若是采集量很大可以使用 BloomFilterDuplicateRemover。若想要调度海量的请求或者有重启续跑这样的需求，则需要自行实现基于数据库（关系型数据库、Redis 等）的调度器。

- **DownloadAgent 下载代理器**: 下载代理器可以部署在不同的机器上，若是单机爬虫则是每个爬虫实例会启动一个单独的下载代理器。下载代理器负责接收需要下载的请求并使用对应的下载器（HttpClient, Puppeteer 或者自定义实现的下载器）。

- **DownloadAgentRegisterService 下载代理器注册服务**: 此服务仅用于接收下载代理器的注册、心跳，即便不启用此服务也并不会影响爬虫的使用。单机爬虫会默认启用一个内存型的注册服务。

- **StatisticsService 统计服务**: 统计各个爬虫和下载代理器的运行状态，如爬虫总的请求数、成功的请求数等，下载代理器总的成功请求数、总的消耗时间等。

- **RequestSupplier 请求供应接口**: 在很多场景下可能下载请求是可以提前知道或存在某个地方（可以是文件、数据库）。

- **RequestConfig 请求配置（Spider.ConfigureRequest）**: 一般情况下请求都可以自动构建好，但在某些特别情况下如加 sign 等，可以统一处理。

- **DataFlow 数据流**: 数据流分两种，解析器和存储器。最极端情况是你不想搞那么复杂，解析和存储都自己在一个 DataFlow 中实现。一个爬虫可以有多个 DataFlow，执行顺序按添加顺序，在任意一个 DataFlow 中抛出异常都会中断整个处理流程。

- **ProxyPool 代理池**: 每个爬虫实例会启动一个代理后台服务，此后台服务定时从注册的 IProxySupplier 中获取新的代理，每个获得的新代理需要经过检测成功才会入到代理池。在配置文件中或者 Builder 创建时可以配置测试地址：ProxyTestUri。

- **ConcurrentController 并发控制器**: 并发控制器以一定速度从 Scheduler 中获取请求并推到消息队列中，这些请求会缓存在 RequestedQueue 中，这个队列是使用低开销的 HashedWheelTimer 实现的，若在一定时间内未收到下载代理器返回的消息，则认为是 Timeout 触发重试直到超过重试次数限制。

# 三、API 接口规范

## 3.1 Agent 与服务端通信接口

### 3.1.1 Agent 注册与认证

- **POST /api/agent/register**: Agent 注册接口
  - 请求体: `{ AgentId, AgentName, IpAddress, Port, Capabilities }`
  - 响应: `{ AgentToken, HeartbeatInterval, ServerVersion }`

- **POST /api/agent/heartbeat**: Agent 心跳上报
  - 请求体: `{ AgentId, AgentToken, CpuUsage, MemoryUsage, TaskCount, Status }`
  - 响应: `{ Ack, NewTasks, ConfigUpdate }`

- **POST /api/agent/unregister**: Agent 注销接口
  - 请求体: `{ AgentId, AgentToken, Reason }`

### 3.1.2 任务管理

- **POST /api/tasks**: 创建采集任务
  - 请求体: `{ TaskName, TaskType, Priority, Requests, Schedule, RetryPolicy }`
  - 响应: `{ TaskId, Status, Message }`

- **GET /api/tasks/{taskId}**: 查询任务详情

- **PUT /api/tasks/{taskId}/pause**: 暂停任务

- **PUT /api/tasks/{taskId}/resume**: 恢复任务

- **DELETE /api/tasks/{taskId}**: 删除任务

- **GET /api/tasks**: 任务列表（支持分页和筛选）

### 3.1.3 任务调度

- **POST /api/agent/tasks/pull**: Agent 拉取待执行任务
  - 请求体: `{ AgentId, AgentToken, MaxCount }`
  - 响应: `{ Tasks, ServerTime }`

- **POST /api/agent/tasks/report**: Agent 上报任务执行结果
  - 请求体: `{ AgentId, TaskId, Status, Result, DataCount, Duration }`
  - 响应: `{ Ack, NextAction }`

### 3.1.4 数据统计

- **GET /api/statistics/agent**: Agent 统计数据
- **GET /api/statistics/task/{taskId}**: 任务统计数据
- **GET /api/statistics/system**: 系统整体统计
- **GET /api/statistics/trend**: 趋势数据（支持时间范围）

### 3.1.5 代理管理

- **GET /api/proxies**: 代理列表
- **POST /api/proxies**: 添加代理
- **DELETE /api/proxies/{proxyId}**: 删除代理
- **POST /api/proxies/test**: 代理测试

## 3.2 统一响应格式

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {},
  "timestamp": "2024-01-01T00:00:00Z"
}
```

## 3.3 错误码定义

| 错误码 | 说明 |
|--------|------|
| 200 | 成功 |
| 400 | 请求参数错误 |
| 401 | 未授权 |
| 403 | 禁止访问 |
| 404 | 资源不存在 |
| 429 | 请求过于频繁 |
| 500 | 服务器内部错误 |
| 1001 | Agent 未注册 |
| 1002 | Token 无效或过期 |
| 1003 | 任务不存在 |
| 1004 | 代理不可用 |

# 四、数据库设计

## 4.1 核心表结构

### 4.1.1 Agent 表 (agents)

```sql
CREATE TABLE agents (
    Id BIGINT PRIMARY KEY AUTO_INCREMENT,
    AgentId VARCHAR(64) UNIQUE NOT NULL COMMENT 'Agent唯一标识',
    AgentName VARCHAR(128) NOT NULL COMMENT 'Agent名称',
    AgentToken VARCHAR(256) NOT NULL COMMENT '认证Token',
    IpAddress VARCHAR(45) NOT NULL COMMENT 'IP地址',
```

# 五、安全机制

## 5.1 Agent 认证与授权

- Agent 注册时生成唯一 Token，用于后续 API 调用认证
- Token 有效期 24 小时，通过心跳接口自动续期
- 支持 Token 吊销和重新生成
- API 调用使用 JWT Bearer 认证

## 5.2 数据传输安全

- 所有 API 通信强制使用 HTTPS
- 敏感数据（密码、Token）传输时加密
- 配置 SSL 证书自动续期（Let's Encrypt）

## 5.3 防攻击措施

- **SQL 注入防护**: 使用参数化查询和 ORM 框架
- **XSS 防护**: 输入验证、输出编码、CSP 策略
- **CSRF 防护**: API 使用 Token 认证，无需 CSRF Token
- **防重放攻击**: 请求签名 + 时间戳 + Nonce
- **请求限流**: 基于 IP 和 Agent 的限流策略（Sliding Window）

## 5.4 敏感数据保护

- 密码使用 BCrypt 哈希存储
- API 密钥、数据库连接字符串加密存储
- 日志中脱敏处理敏感信息
- 配置环境变量管理敏感配置

# 七、异常处理与容错机制

## 7.1 网络异常处理

- **重试策略**: 指数退避重试（Exponential Backoff）
  - 初始延迟：1 秒
  - 最大延迟：60 秒
  - 最大重试次数：可配置（默认 3 次）

- **熔断机制**: 连续失败达到阈值时熔断，避免雪崩效应

- **超时控制**: 分层超时设置（连接超时、请求超时、总超时）

## 7.2 任务失败处理

- **失败分类**:
  - 网络错误：自动重试
  - 目标网站反爬：切换代理或降速
  - 数据解析失败：记录错误，跳过该请求
  - Agent 异常：重新分配给其他 Agent

- **死信队列**: 超过最大重试次数的请求进入死信队列，人工介入处理

## 7.3 数据一致性保障

- **幂等性设计**: 所有 API 接口支持幂等操作
- **分布式锁**: 使用 Redis 实现分布式锁，防止并发冲突
- **事务管理**: 关键操作使用数据库事务
- **补偿机制**: 任务状态不一致时自动修复

## 7.4 断点续传机制

- 任务进度持久化到 Redis 和数据库
- Agent 重启后从最后成功的位置继续执行
- 支持手动指定重试起始点

# 八、异常任务标记与恢复机制

## 8.1 异常任务标记

### 8.1.1 任务状态追踪

- **任务级状态**: 记录每个任务的总体执行状态（待执行、执行中、暂停、失败、已完成）
- **请求级状态**: 记录每个采集请求的执行状态（待执行、执行中、成功、失败、超时）
- **失败原因分类**: 
  - 网络错误（连接超时、DNS 解析失败）
  - 目标网站错误（4xx、5xx 响应）
  - 解析错误（数据格式异常）
  - Agent 异常（进程崩溃、资源耗尽）
  - 业务错误（反爬拦截、验证码）

### 8.1.2 异常任务标记规则

- 单次请求失败自动标记并记录失败原因
- 连续失败超过阈值（可配置，默认 3 次）标记为"异常任务"
- Agent 异常离线时，其执行中的所有任务自动标记为"待恢复"
- 任务执行时间超过预期时间（可配置）标记为"超时任务"

### 8.1.3 异常任务存储

- 异常任务信息持久化到 `task_requests` 表的 `Error` 字段
- 异常任务统计记录到 `statistics` 表
- Redis 中维护异常任务集合，便于快速查询

## 8.2 任务恢复机制

### 8.2.1 自动恢复策略

- **Agent 重连恢复**: Agent 重新连接后，自动拉取之前未完成的"待恢复"任务
- **请求级重试**: 失败的请求根据重试策略自动重新入队
- **任务级恢复**: 失败的任务在满足恢复条件后自动恢复执行

### 8.2.2 手动恢复机制

- Portal 提供异常任务列表，支持手动操作
- 支持的操作：
  - **重新执行**: 重新执行失败的任务或请求
  - **跳过**: 跳过无法恢复的请求，继续执行后续请求
  - **终止**: 终止无法恢复的任务
  - **导出**: 导出异常任务详情，便于人工处理

### 8.2.3 恢复流程

```
1. 检测任务异常
   ↓
2. 标记任务状态为"失败"或"待恢复"
   ↓
3. 记录失败原因和当前进度
   ↓
4. 触发恢复策略判断
   ↓
5. 自动恢复 或 等待手动处理
   ↓
6. 恢复执行
   ↓
7. 更新任务状态
```

## 8.3 任务状态机

```
待执行 → 执行中 → 已完成
    ↓        ↓
    ↓     失败 → 待恢复 → 执行中
    ↓        ↓
    ↓     暂停 → 恢复 → 执行中
    ↓
  已取消
```

## 8.4 进度保存与恢复

### 8.4.1 实时进度保存

- 每完成一个请求，更新任务进度到 Redis
- 定期（默认 30 秒）将 Redis 中的进度同步到 MySQL
- Agent 心跳时上报当前执行进度

### 8.4.2 恢复点管理

- **请求级恢复点**: 记录最后成功执行的请求 ID
- **分页恢复**: 对于分页采集任务，记录当前页码
- **游标恢复**: 对于增量采集任务，记录最后处理的数据游标

### 8.4.3 数据一致性保障

- 恢复执行前检查已采集数据，避免重复采集
- 使用请求 ID 进行去重，确保幂等性
- 支持断点续传的数据合并

## 8.5 异常任务监控

### 8.5.1 告警规则

- 任务失败率超过阈值（默认 10%）触发告警
- 异常任务数量超过阈值触发告警
- 任务执行时间超过预期时间触发告警
- Agent 离线导致任务中断触发告警

### 8.5.2 统计报表

- 异常原因分布图
- 任务恢复成功率统计

2. 数据库初始化脚本（包含表结构和初始数据）
3. Docker 相关配置文件（Dockerfile、docker-compose.yml 等）
4. 系统部署文档和使用手册（包括 README 文件）

项目开发需确保代码可维护性和扩展性，便于未来功能升级和内容更新。
